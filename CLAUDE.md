# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Interactive character sheet for the tabletop RPG **World of Dungeons** (©1979 J.S. Harper with C. McDowell, One & Seven Tactical Design Institute, Seattle, WA). Mobile-first web app with three interface modes: character creation, in-game play (single character or shared party view), and level-up flow. Online, characters live in games: a master and players share one table, and teammates' sheets open read-only.

## Commands

```bash
npm run dev       # Nuxt dev server, http://localhost:3000
npm run build     # nuxi typecheck (vue-tsc, strict) + nuxt generate into .output/public
npm run preview   # serve the generated build
npm run test      # unit tests (vitest project `unit`, watch mode); add --run for one-shot, --coverage for coverage
npm run storybook        # Storybook dev server on :6006
npm run test-storybook   # runs every story and its play function in headless Chromium (vitest project `storybook`)
npm run build-storybook  # static Storybook into storybook-static/
```

Node 24 from `.nvmrc`, npm 11. `nuxt dev` (`@nuxt/cli` here) can crash at start with `options.hostname.toLowerCase is not a function` when no host is given: pass one, `npm run dev -- --host localhost`. Before the first `test-storybook`, install the browser: `npx playwright install chromium`. `postinstall` runs `nuxt prepare`, which generates `.nuxt/` (the root `tsconfig.json` references its tsconfigs).

Run a single test file: `npm run test -- app/utils/derived.test.ts`.

`npm run test-visual` compares every story against the local baseline in `.visual/baseline/` (gitignored). Never run `test-visual:update` unless the baseline is meant to change. `CI=true npm run test-visual` compares without writing a baseline for a story that has none (it fails instead). A mismatch writes the actual and the diff images to `.visual/diff/<story file>/<story>-actual.png` and `-diff.png`.

## Tech Stack

- **Framework**: Nuxt 4 in SPA mode (`ssr: false`, static `nuxt generate`), Vue 3 + TypeScript (strict). Application code lives in `app/`; `@/` points at `app/`
- **Auto-imports are off** (`imports.autoImport: false`, `components.dirs: []`). Every file imports what it uses explicitly, components included
- **Nuxt APIs** (`#app`, `#imports`, `#components`: `definePageMeta`, `defineNuxtRouteMiddleware`, `navigateTo`, `useRuntimeConfig`, `defineNuxtPlugin`, `NuxtPage`) are used only in `app/pages/`, `app/middleware/`, `app/plugins/` and `app/app.vue`. Components, composables and stores never import from them, so Storybook renders them without a Nuxt runtime; pass the value in as a prop or wrap it instead. They keep using `useRoute`/`useRouter` from `vue-router`
- **Startup**: `app/plugins/02.bootstrap.client.ts` points PocketBase at `runtimeConfig.public.pbUrl` (from `VITE_PB_URL` at build time) and picks the mode from the first URL (`utils/routeMode.ts` `initialMode`: `/offline…` and the landing `/` start offline, everything else online; see *App modes*). In online mode it awaits `restoreSession()` (refreshes the saved sign-in) and then `bootstrap()` before the first navigation and render; `bootstrap()` does nothing while signed out, and `app.vue` shows the sign-in screen instead; `bootstrap()` subscribes to realtime and then fetches the data under one `BOOTSTRAP_TIMEOUT_MS` (6 s) deadline, so a hanging server delays the first render instead of blocking it. In offline mode it calls `startOfflineSession()` and sends nothing to PocketBase
- **State / Persistence**: Pinia. Where the data lives depends on the app mode (see *App modes*): online data lives on the server, offline data in localStorage. localStorage keys: `pocketbase_auth` (the SDK's sign-in token), `wod.offline.characters.v1`, `wod.offline.rolls.v1`, `wod.offline.changes.v1` (hand-rolled in `app/transport/offlineStorage.ts`), `wod.creation.v2` and `wod.media.v1` (`pinia-plugin-persistedstate`; the second is this device's sound, volume and scene-background choice, kept across sign-out and mode switches), `wod.locale.v1`. The old `wod.characters.v1`, `wod.rollHistory.v1`, `wod.creation.v1`, `wod.mode.v1` (the old mode switch) and `wod.home.tab.v1` (the old Home tabs) keys are dead; nothing reads them
- **UI Primitives**: [Reka UI](https://reka-ui.com/) (dropdowns, popovers, dialogs, tabs)
- **3D Dice**: `@3d-dice/dice-box-threejs` wrapped in `app/services/DiceAnimationQueue.ts`
- **Scene audio**: `app/services/SceneAudio.ts` is the pure logic (unit-tested with fake tracks). `createAudioMixer(deps)` holds the channels and what they share: `blocked` (true while any channel is), `unlock()` (resumes every channel's waiting track whenever the shell's resume settles, but keeps its caller waiting at most `UNLOCK_WAIT_SECONDS` (1), since a resume outside activation can stay pending forever), `setVolume`, `stop()`, `arm()` (until the pool has been primed this page session, with the context running, the next activating event anywhere unlocks, which primes it, so a later sound plays without a refusal; it is harmless to call again and never resumes a deliberate pause; the primed state comes from the shell's `primed()` after an unlock), and a document gesture listener installed while a channel is blocked by something a tap fixes, or while armed and not primed (a refused play, a suspended context; not a deliberate pause from outside, which only an explicit `unlock()` resumes: the prompt's button, the sound control): every activating event unlocks, and the listener stays until that block clears, because an event can turn out to carry no activation; a tap that unlocks one channel never resumes another channel's deliberate pause (`resume(byTap)`). A channel (`mixer.channel()`) plays at most one audible track plus one incoming one: `request({ key, src, loop, fade } | null)` crossfades over the request's `fade` once the new track can play (the latest call wins; the same `key` again does nothing, a new `key` restarts even the same `src`; the old track fades out, then is paused and released); `hold(fade)` fades the playing track out and pauses it in place, and a request meanwhile is prepared but kept silent; `release(fade)` brings that request in, or plays the held track on from where it paused; `onEnded(listener)` reports the key of a non-looping track that finished by itself (that key then stays requested: asking for it again does nothing until null or another key; a media error clears it, so a failed key may be retried), `onStarted(listener)` the key of a request whose track has just started playing as the current one (while held: on release), `onIdle(listener)` each time the channel is left with no current track and none incoming; its own `blocked` is a refused play or an interruption of its current track (never while held), cleared when the browser brings the track back by itself (`onResumed`), and `resume()` (after an unlock) plays the refused track or resumes the interrupted one where it stopped. A media error after start blocks nothing: the track goes, it is logged, and the same `src` may be asked for again. A refused incoming track still fades the previous one out, so a wrong sound never keeps playing under the new picture. The channel pins a track from the moment it is ready (so before its play is attempted, and while a refused one waits for a tap) and while it is current or held, so the pool never takes its element, and treats a track call that throws as done, so a transition always completes. Its computeds and that watcher live in a detached `effectScope(true)`, so the component that first calls `sceneAudio()` cannot take the listener with it when it unmounts. `createSceneAudio(deps)` is the mixer with a scene channel (key = src, loop, `SCENE_FADE_SECONDS` = 2) and an overlay channel (the master's sound over the scene: `OVERLAY_FADE_SECONDS` = 1): `setScene(src | null)`, `setOverlay({ key, src, loop } | null)` (the same key again does nothing, and a key that already played to its end is not played again until null or another key, so re-applying the same stage never replays a finished cue), `onOverlayEnded(listener)` (the key of a non-looping overlay that finished by itself, not one stopped or replaced; returns an unsubscribe; a listener subscribed twice is called twice), `setVolume`, `unlock()`, `arm()`, `stop()` (both channels), `blocked` (either channel). The overlay channel is made first, so an unlock tries the overlay before the scene: with both refused, the scene's start then usually finds itself held. The scene is held only once the overlay actually plays (a loading, failed or refused overlay leaves it playing): it fades out over 1 s and pauses while the overlay fades in, and stays held across a replacement (a new key crossfades on the overlay channel). When the overlay is stopped (it fades out over 1 s), ends by itself (released at once, then `onOverlayEnded`) or errors (dropped, without `onOverlayEnded`), the scene comes back from where it paused over 1 s; a scene asked for meanwhile is prepared silently and is what comes back, `setScene(null)` meanwhile leaves nothing. An outside pause or a suspended context blocks the overlay like the scene, and the scene stays held. Pool arithmetic: whenever a track is created, at most three other tracks are neither fading out nor free (the requesting channel's current, the other channel's current and incoming), so with 6 elements, and every fading track unpinned at a last fade target of 0, an eviction always takes a fading track. `webAudioTrack.ts` `webAudioDeps(env?)` is the browser shell (`env` injects `Audio`, `AudioContext`, timers and `document` for its tests): one `AudioContext` with a master gain (never suspended by the app: WebKit may refuse a later resume without a gesture) and a pool of `POOL_SIZE` (6) `<audio>` elements, each made once with its source and gain node (volume and fades on gain nodes, since iOS ignores `element.volume`) and reused by changing `src`: a free one silent longest first, then a new one; with all taken, an unpinned one whose last fade went to 0, then the unpinned one taken longest ago, ramped to silence over `STEAL_RAMP_MS` (30) before its new `src` if it was still audible. `dispose()` returns the element paused, without `src`, at gain 0, with its listeners and ready timer gone, and a disposed or evicted track never touches it again (an evicted track's `play()` rejects with `AbortError`, also when the element's play was already under way); no `Track` method throws. `unlock()` runs inside the gesture: it fills the pool and plays every element not yet primed once (a free one on a silent WAV, which is removed again; an owned one on its own src) and pauses it, since WebKit lets an element play without a gesture only after one played inside a gesture; an element counts as primed only from that play's outcome (allowed, or aborted by the pause, not `NotAllowedError`), so a call outside activation leaves it for the next one; then it waits on `context.resume()` with no time limit, asking again on every call, and on the priming plays' outcomes, so `primed()` (the whole pool primed) is current when it settles. A looping track is `ready` on `canplaythrough` or after `READY_FALLBACK_SECONDS` (6; iPhones may never fire it before play); a one-shot on `canplay` or after `ONE_SHOT_READY_FALLBACK_SECONDS` (1.5), since a cue is timed to the master's click and `play()` resolves only once playback really starts; `play()` without a gesture bounds the resume by `RESUME_GRACE_MS` (a resume without a gesture can stay pending forever), after which it rejects as `NotAllowedError`. `onInterrupted(cause)` reports `'error'` after start, `'paused'` for a pause the service did not ask for (not the end of a track) and `'suspended'` for the context leaving `running` while a track plays; `onResumed` the element playing again, or the context running again, by itself. Every gain change goes through one guarded helper (`cancelScheduledValues(0)`, then an equal-power curve from the current gain, `equalPowerCurve`, `CURVE_POINTS` 33; on a refusal a linear ramp; then the bare value), since the spec refuses any automation inside an active curve. `addGestureListener` listens in the capture phase for the events that carry user activation (a mouse press, a touch or pen release, `touchend`, `click`, a key other than Escape) until its remover is called. `sceneAudioInstance.ts` `sceneAudio()` is the app's one instance, made on first use; Storybook aliases it to a mock
- **Routing**: Nuxt file-based pages in `app/pages/` (vue-router underneath); guards are named route middleware in `app/middleware/` over pure functions in `app/utils/routeGuards.ts`
- **Tooling globals**: Storybook builds through `viteFinal` + `.storybook/vite.shared.ts`. `__APP_VERSION__` and `__BUILD_TIMESTAMP__` are frozen there on purpose (the visual baseline depends on them) — do not make them read `package.json`. A new global define or alias must be added to `nuxt.config.ts`, `vitest.config.ts` and `.storybook/vite.shared.ts`, and declared in `app/types/globals.d.ts`. The exception is a Storybook-only mock under `.storybook/mocks/`, aliased in `vite.shared.ts` alone: `pb`; `upload` (`sendForm` without XHR); `diceAnimationQueue`, which stubs the dice queue because stories have no 3D scene (`isAnimating` stays false, unless a story sets the mock's `animatingMock` to show the rolling state and puts it back); and `sceneAudioInstance`, which never touches Web Audio: it records the calls (`sceneAudioCalls`, `setOverlay` and `arm` included), a story sets `blockedMock` and fires a finished overlay with `fireOverlayEnded(key)` (its reset keeps the overlay-ended listeners, which unsubscribe themselves) (helpers in `app/stories/playback.ts` and `scenes.ts`)
- **Testing**: Vitest + happy-dom + `@vue/test-utils`. Coverage of **domain core only** — `app/utils/derived.ts`, `app/domain/reducer.ts` and the route guards in `app/utils/routeGuards.ts`, `app/utils/permissions.ts` (incl. `canGiveFromLibrary`). Do not add unit tests for UI/stores/composables — UI behaviour is covered by Storybook stories with `play` functions, which CI runs.

## Routes

Route names are set with `definePageMeta({ name })` and used by `router.push({ name })` and `app/stories/router.ts`; keep them stable.

Three areas, and the address decides the mode (*App modes*):

- **Public, no sign-in:** the landing `/` and the offline table under `/offline`.
- **Cabinet, sign-in required:** `/games`, `/characters`, `/profile`, the game tables, the free-characters table, `/join/<code>`. Signed out, `app.vue` shows the sign-in screen in place of the page and keeps the URL.

**Shells.** `app.vue` picks the frame from the page's `meta.shell` (typed in `app/types/router.d.ts`): `bare` renders the page alone, without panels and without the sign-in gate (the landing); `cabinet` renders it in `CabinetLayout` (the cabinet header, a centred column, no table panels) behind the gate; no `shell` means the table: `GameLayout` with `PlayersPanel` and `DiceDrawer`, behind the gate except under `/offline`. `app.vue` must read the route with vue-router's `useRoute`, not Nuxt's: Nuxt's follows the rendered page, and the sign-in screen renders none, so leaving it (back to the landing, "Play offline") would never update it.

## Data Model

Central type: `Character` (`app/types/character.ts`).

- `Stats` — six stats (`str/dex/con/int/wis/cha`), each stored as the **bonus** (not raw 2d6 roll)
- `StatModifier { id, statKey, amount, label }` — temporary buff/debuff stack on a stat
- `InventoryItem.descriptor: ItemDescriptor` — discriminated union: `weapon` (melee/ranged), `armor` (`class: 'none'|'light'|'full'`), `shield`, `gear`, `tool`, `occult`, `custom`. `equipped?: boolean` flags the active item. Players no longer create or edit items (`ADD_CUSTOM_ITEM` / `EDIT_CUSTOM_ITEM` are gone); stored items of kind `custom` still render and can be equipped, removed and spent.
- Library (`app/types/library.ts`): `LibraryMonster` and `LibraryItem`, the master's per-game entries. `checkMonster` / `checkItem` in `app/domain/library.ts` are the one shape check (normalise or return problems); `libraryItemToInventory` turns an item into an `InventoryItem` for `RECEIVE_ITEM`. `InventoryItem.libraryItemId` links a handed-out item to its library entry, and consumables stack by it; `templateId` stays reserved for the built-in gear catalog, and the two never stack with each other.
- Starter library (WODU-10, `app/domain/starterLibrary.ts`): `starterMonsters()` (stats in `app/data/starterMonsters.ts`, names and specials in `content.starterMonsters`) and `starterItems()` (the whole of `GEAR_CATALOG`) build read-only `LibraryMonster` / `LibraryItem` entries in the current language. They are static content, never stored, with ids `starter-<id>`. A starter item carries `LibraryItem.templateId`, so `libraryItemToInventory` hands out the catalog item itself (`templateId`, no `libraryItemId`): the name follows each viewer's language and it stacks with bought ones. A copy goes through the usual form and is an ordinary game entry with no tie to the catalog; it keeps its use-effect, which lives on the entry.
- Encounter (WODU-11, `app/types/encounter.ts`, rules in `app/domain/encounter.ts`): `EncounterMonster` (an instance copied from a library entry: `sourceId`, `n`, name, HP / max HP, armor, damage, special, notes, `conditions` (nine fixed text tags in `CONDITIONS`, no mechanical effect), `touchedAt`, `diedAt`), `EncounterState` (one per game, record id = game id: `sortMode`, `manualOrder`, `counters`: the next number per `sourceId`, kept apart so a removed instance's number is never reused) and `EncounterHit` (one applied roll: `rollId`, target, source name, roll total, armor, amount; append-only, master only). `checkEncounterMonster` / `checkEncounterState` / `checkEncounterHit` are the shape checks. `damageAfterArmor(total, armor)` is `max(0, total - armor)`; `canApplyRoll` decides which log rows a selection is offered. Instances are snapshots: later library edits or deletion never touch them.
- Stage, scenes and sounds (WODU-60, `app/types/stage.ts`, rules in `app/domain/stage.ts`): a `Scene` is the master's named pair of an image and / or a sound (`image`, `sound`: the stored file names, `null` when absent; at least one, `checkSceneDraft`). The `Stage` is what a game's table shows, one per game (record id = game id): `scene` (`{ id, image, sound }` as `FileRef`s `{ collection, record, name }`, or `null`), `sound` (the one sound the master plays over the scene, `{ id, file, loop, startedAt }`; `overlayKey` is `id:startedAt`, so every play is a new key) and the `image` slot of the single picture the master shows (`{ id, file, caption, shownAt }`; the Images panel writes it). A `Sound` is the master's entry: `name`, `loop`, `duration` (seconds, read in the browser by `utils/audioDuration.ts` at pick time, `null` when unknown) and the stored `file` (`checkSoundData`, `checkSoundDraft`). A one-shot found in a loaded stage plays only within `STALE_ONE_SHOT_SECONDS` (5) of its `startedAt` (`shouldPlayOverlay(sound, now)`; the overlay memory below calls it). A scene's name never enters the stage (it can be a spoiler), and files go up under a neutral name (`neutralFileName`: `image.<ext>` / `sound.<ext>`), since PocketBase keeps the uploaded name inside the stored one. `MEDIA_LIMITS` (20 scenes, 15 sounds and 30 images per game), images JPEG / PNG / WebP up to 2 MB (`IMAGE_MAX_BYTES`; `utils/fitImage.ts` re-encodes a larger or other picture to WebP, or to JPEG on a dark token fill where the browser cannot write WebP, lowering quality, then halving the size, until it fits; its `ImageFitError` is told under the picture field), sounds MP3 / M4A / AAC up to 20 MB (`AUDIO_MAX_BYTES`); `checkUpload`, `checkSceneData`, `checkStage` (lenient: a malformed slot reads as empty) are the shape checks. `withScene` / `withoutScene` / `withSound` / `withoutSound` / `withImage` / `withoutImage` build the next stage (`withImage(stage, image, withCaption, shownAt)` puts the caption in only when asked and present; `withImageEdited` follows a save of the shown image without a new reveal and never adds a caption the stage lacks; an image is a `TableImage` `{ id, caption, file }`, `checkImageData` / `checkImageDraft` its checks with `CAPTION_MAX` 120; `revealKey` is `id:shownAt` and `shouldReveal(previousKey, nextKey, isMaster)` the pure rule for a picture popping up: the first value seen never, the master never), `fileUrl(base, ref, thumb?)` the file address (base = `pb.baseURL`), and `playbackTarget(stage, prefs, base)` what one device fetches: a URL only for what that device has on, so what is off is never downloaded (its `overlay` is the stage's sound whenever sound is on; whether it plays is the overlay memory's decision). `nextSoundArrival` moves the sound slot's arrival only when the slot's key changes, `oneShotClearDelay` and `oneShotOverDelay` are the clear's and the row's clocks (see `useOneShotClear`)
- `Magic` — optional, only when class/abilities grant a magic section (cleric, wizard, etc.)
- `CharacterStatus` — `'draft'` (creation in progress) | `'active'` (fully created)
- `hpHistory: { level, roll, source: 'dice'|'sturdy' }[]` — every HP roll, per level

**Armor has no dedicated field.** `totalArmor` is computed from equipped inventory: `light` armor → 1, `full` → 2, `shield` → +1, plus `toughness` ability.

`ClassData` (`app/data/classes.ts`) drives starting skills/abilities per class.

## Domain Layer (`app/domain/`)

All gameplay state mutations go through commands. **Never** mutate `Character` from a component or composable.

- `commands.ts` — `CharacterCommand` discriminated union (~25 command types: inventory, combat, progression, stat modifiers, draft-only creation commands, misc)
- `reducer.ts` — `applyCommand(char, cmd): Character` — pure function, returns a new character
- `inventory.ts`, `combat.ts`, `progression.ts`, `creation.ts`, `modifiers.ts` — domain logic modules consumed by the reducer

Flow: composable → `store.dispatch(id, cmd)` → `applyCommand` → `backend()` write (PocketBase online, localStorage offline). The creation wizard dispatches draft-only commands the same way.

## Derived Values (`app/utils/derived.ts`)

All computed/derived values live here — never recalculate inline in components.

- `totalArmor(char)` — equipped armor tags + `toughness`
- `damageAbilityBonus(char, weapon)`, `damageFormulaCompact(char, weapon)`, `damageFormulaParts(char, weapon)` — weapon damage with ability bonuses (`skirmish`, `hewing`, `volley`, etc.)
- `hpBreakdownLines(hpHistory)`, `damageBreakdownLines(char, weapon)`, `armorBreakdownLines(char)` — formatted rows for `InfoPopover`
- `isReadyToLevelUp(char)` — XP vs `XP_THRESHOLDS`
- `rollHitDice(numDice, level)` — rolls N d6, keeps top `level`
- `statBonusFrom2d6(roll)` — 2d6 → bonus (0/1/2/3)

`BreakdownLine { value, label }` is the shared interface for popover rows — `label` is a `LabelRef` (`{ key, params? }`), resolved with `tLabel()`, not a plain string.

Ability bonuses are **data-driven**: `app/data/abilities.ts` exposes `ABILITY_EFFECTS` and `getAbilityEffect(id)`. `derived.ts` reads this table — do not branch on ability IDs (`if (id === 'hewing')`) anywhere else.

Item use-effects similarly: `InventoryItem.useEffect` (`'quicksilver'`) drives `domain/inventory.ts` — do not hardcode item IDs or look the effect up in the catalog. Catalog items get it through `catalogItem(tpl)`, library items from the entry (`LibraryItem.useEffect`, set by the master on any consumable with "Counts as quicksilver"). All such items share one daily limit, `quicksilverCount` against the level, and the Magic panel's button drinks the first one in the inventory.

## App modes (`app/transport/`)

Two modes, and **the address decides which**: under `/offline` the offline mode, everywhere else (but the landing) the online one. There is no switch. Online and offline data are fully separate: nothing syncs, imports or exports between them.

- **Online**: the cabinet and the game tables, only for signed-in accounts (see *Accounts*). PocketBase is the store. Each account sees its own characters plus those of the games it is a member of: creates send `owner` and `game`, events send `character` and `game` (`transport/rows.ts`). The initial load comes from `bootstrap()`, realtime carries the account's other sessions and the other members of its games, and writes go to the server optimistically, rolling back on failure. No game data is kept on the device; only the creation draft pointer is.
- **Offline**: the offline table under `/offline`, no account needed. Characters, roll history and the change log live only on the device, under the `wod.offline.*` keys. Writes never roll back, and no request goes to PocketBase (the `CharacterListView` stories `OfflineTableSendsNothing` / `EnteringOfflineSendsNothing` and the `PanelFooter` `Offline` story check it). The panel shows an offline badge and a hint that clearing site data deletes these characters; its footer keeps the language switch, since there is no profile offline.

Offline has no games, scope or read-only sheets: `canEditCharacter` is always true and the guards send people to `/offline`.

**How the mode follows the address.** `utils/routeMode.ts`: `modeForPath(path)` (`'offline'` under `/offline`, `null` for `/`, `'online'` otherwise) and `initialMode(path)` for the bootstrap plugin. The global middleware `middleware/mode.global.ts` calls `transport/modeSwitch.ts` `enterMode(modeForPath(to.path))` on every navigation: stop the current mode, `setMode` (bumps `modeSession`), clear the three stores, then `startOfflineSession()` or `restoreSession()` + `bootstrap()`. Global middleware runs before a page's own, so the target's guards see its data. The creation draft pointer (`wod.creation.v2`) is kept per mode, so each mode resumes its own draft.

**The mode switches in `beforeEach`, before the navigation commits.** The old page is still mounted in the new mode until the new one renders, and an aborted guard or a failed lazy chunk would leave the old page in the new mode. So a mounted view that reacts to `mode` or `onlineDataReady` (they flip at the switch: offline data counts as loaded at once) must check the mode it was opened in before acting, as `JoinView`, `CharacterCreationView` and `useRouteRecheck` do. No current guard redirects across areas.

- `mode.ts` — `mode` ref, `setMode`, and `modeSession()`, a counter that lets an in-flight online write detect a mode switch and drop its result
- `backend.ts` — the `Backend` interface the stores and the dice roller write through; `backend()` returns `pbBackend` or `localBackend` for the current mode
- `bootstrap.ts` — online load (subscribe first, then fetch, under one timeout; realtime events that arrive during the fetch are replayed on top of it), `reloadOnline()` after a reconnect, `stopOnline()`; exports `onlineDataReady`, which the route guards and the character list wait for
- `connection.ts` — `connection` state (`ok` / `checking` / `down`). A network failure (failed write, realtime drop, the browser firing `offline`) starts a `GRACE_MS` (3 s) grace period that ends with one `/api/health` check: if the server answers, the state goes back to `ok` and no overlay is shown (a single failed write or a Wi-Fi/cellular handover never raises it); only if the check fails does it go `down`, and a backoff loop then probes `/api/health`, reloads and resubscribes when it answers. The browser's `online` event triggers a check at once (`probeNow()`). `problemOutcome()` tells a failed write how the problem ended, so `transport/writeFailure.ts` shows the `errors.*Failed` toast when the server was reachable after all (the change was rolled back) and leaves it to the overlay otherwise
- `writeFailure.ts` — `reportWriteFailure(err, message, session)`, the toast policy for rolled-back writes described above
- `offlineStorage.ts` — offline load, persistence watcher, toasts for unreadable data or a failed write; picks up changes another offline tab writes (`storage` event) instead of overwriting them
- `modeSwitch.ts` — `enterMode(next)` and `startOfflineSession()` (see above)
- `scope.ts` — `scope` ref (`home` | `solo` | `game`) and `setScope`. `app.vue` sets it from the route (`useTable().tableScope`, from `utils/scope.ts` `scopeForRoute`): `game`, `game-party`, `game-character-new`, `game-settings`, `game-monsters`, `game-items` → that game; online `party` → `solo`; `level-up` → its character's game; everything else (the cabinet pages included) and all of offline → `home`. All visible characters are loaded up front; only roll/change events matching `eventFilter(scope)` are fetched (home fetches none), and realtime events failing `eventInScope` are dropped; a scope change reloads the two event stores and re-reads the game's characters
- `games.ts` — online-only game operations, each through `guard()` with the bootstrap timeout and a `staysCurrent()` check (same mode session and user): `findGameByCode` (list endpoint filtered by `invite_code`, works signed out), `createGame` (game, then own membership; the game is deleted if the membership fails; code collisions retry), `joinGame` (game into the store, membership with the code, then `loadGame`), `leaveGame` (free own characters there, delete membership, `forgetGame`), `removeMember` (free that member's characters, drop them locally, delete membership), `resetInviteCode`, `renameGame(gameId, name)` (trimmed, 1–80 characters as on create, `utils/gameName.ts`), `transferMaster(gameId, userId)` (only to another member; the store takes the new master as soon as the server answers, realtime brings it to the others), `deleteGame`, `claimMaster` (update `master`, read back; `MasterTakenError` if someone else won), `moveCharacter(id, gameId)` (`''` takes it out), `assignCharacter(id, userId)`. `forgetGame` drops a game, its members and teammates' characters locally, because the server sends nothing for records that stop being readable. `healStuckCharacters(gameId?)` (after every load and in `forgetGame`) takes my characters out of a game I am not a member of (`moveCharacter(id, '')`): the server hides them and refuses their rolls until then
- `onlineOps.ts` — `call` (guard + bootstrap timeout), `requireOnlineUser`, `staysCurrent`, shared by `games.ts` and `library.ts`
- `library.ts` — the master's library of monsters (WODU-8) and items (WODU-9): `loadMonsters(gameId)` / `loadItems(gameId)` (into `useLibraryStore`; entries failing `checkMonster` or whose `data.id` differs from the record are dropped; a failure leaves the store `failed`), `createMonster` / `createItem`, `updateMonster` / `updateItem` (send only `data`), `deleteMonster` / `deleteItem` (`(gameId, id)`; items follow the monsters' semantics, entries are checked with `checkItem`) (the server answers 404 both for a gone entry and for a non-master, so a 404 re-reads the game: still the master → deleted; otherwise the new master goes into the store and the delete fails). Loaded when the screen opens (and again after a server outage), not by `bootstrap()`, and no realtime subscription: only the master reads the collection, so the only other writer is the master's own other device
- `encounter.ts` — the master's encounter (WODU-11) over three master-only collections, `encounters` (one row per game, id = game id), `encounter_monsters` and `encounter_hits` (append-only). `openEncounter(gameId)` loads them and subscribes to all three (so the master's other devices stay in step; an incoming monster row older than the local copy by `touchedAt` is ignored, so an echo of an earlier write cannot roll HP back), `closeEncounter()` drops the subscriptions, `addMonster(gameId, entry)` (serialised; takes the next number from `counters`), `saveMonster`, `removeMonsterInstance`, `saveEncounterState`, `recordHit` (the hit is kept locally first, so a failed write still blocks a second application; the error is rethrown and `useApplyHit` retries, then shows `errors.encounterHitFailed`). Writes are optimistic with rollback and a toast; what waits behind a write in flight is dropped once the mode or the user changes, so nothing reaches PocketBase offline. A reopen of the same game is a refresh in place: the status stays `ready`, so the log's Damage filter and an open popup live through a dropped connection, and a refused refresh keeps the list with a notice (`refreshFailed`). A monster's `touchedAt` always moves forward (`max(now, previous + 1)`), so clock skew between the master's devices cannot get an edit dropped as stale. Two limits of a hit are accepted: its writes are not atomic, so a monster's HP write that fails later (after a rollback) still leaves the hit, and a character's write that landed but reported failure records no hit, so that roll can be applied again; both are corrected by hand through HP. Only the master requests these collections; a player never does, and the server lists nothing to them. The session follows the table: `composables/useEncounterSession` (called once in `app.vue`) opens the encounter while the open table is a game I master and the server is reachable, and closes it otherwise, so a master transfer takes the panel from the former master at once; `retryEncounter()` is the panel's Try again. Monster dice are written as `roll_events` with `character` empty and `game` set (the rule's second branch: the caller is the game's master); `monsterRollBody` in `rows.ts` builds the row, with `character_id` and `data.characterId` holding the instance id
- `stage.ts` — the stage (WODU-60), read by every member, written by the master. `bootstrap()` lists all readable `stages` rows fail-soft (its own 4 s limit inside the bootstrap deadline; a refused or missing list is logged and treated as no stages, because the stage is decoration) and subscribes to them softly; `applyStages(rows)` applies a snapshot after the games are in the store (rows of unknown games ignored, a malformed row keeps what is shown, a game without a row shows nothing), `receiveStage` a realtime event. A game joined later loads its stage in `loadGame` (`games.ts`), by a list filtered by id, since `getOne` on a game with no row logs a 404. `publishStage(next, { quiet? })` (master; `quiet` leaves out the failure toast, for the clearing of a finished sound nobody asked for, and holds only while every publish folded into the write was quiet) is optimistic through the serial writer: one write in flight per game, the newest waiting value replaces older ones, a failure restores the last confirmed stage with `errors.stageFailed` and rejects; `WriteDropped` when the mode or the user changed first. A game's first publish creates the row, later ones update it: it remembers which rows it has seen (snapshot, realtime, its own writes), so once a row was seen or created no publish logs a 404; after a fail-soft stage-list failure a master's first publish may log one refused create before it updates. While a publish is pending, echoes for that game are ignored. The `stages` and `scenes` collections and their rules come from the `wodu-api` migrations `1700001200_account_limits.js` and `1700001300_table_media.js`; against a backend without them the stage load fails soft and the table works without scenes, but the master's Scenes panel shows its load-failed state
- `serialWriter.ts` — `serialWriter({ show, restore, send, message, settled })`: the per-key optimistic writer behind `publishStage` (`submit`, `forget`, `busy`; `WriteDropped`)
- `media.ts` — the master's table media (scenes, sounds and images; a kind joins by one entry in the `mediaKinds` table: collection, `fromRow`, file fields with kind and required flag, limit, `checkDraft`, `stored`, optional `live` hooks) over collections which only the game's master lists, reads and gets events for (WODU-60). One generic path (`createMedia` / `updateMedia` / `republishMedia` / `deleteMedia`, each taking the kind first) holds every guard below; `createScene` / `updateScene` / `republishScene` / `deleteScene` and `createSound(gameId, draft, file, onProgress?)` / `updateSound(gameId, sound)` / `deleteSound` are thin wrappers (`createImage(gameId, { id, caption }, file, onProgress?)` / `updateImage(gameId, image, file?, onProgress?)` / `republishImage` / `deleteImage` likewise: an image has one required `file`, fitted like a scene picture and uploaded as `image.<ext>`, and a caption of at most 120 characters in `data`; saving the shown image re-publishes it through `withImageEdited` (new file, same `shownAt`, a stage caption of null stays null, nothing is written when the stage would not change) and deleting it takes it off the stage first; a sound's draft is `{ id, name, loop, duration }`; `updateSound` sends data only, since the file never changes, and never re-publishes: a changed name or loop flag applies from the next play; deleting the playing sound takes it off the stage first), and `mediaThumb(ref, size)` builds a thumbnail URL. `openMedia(gameId)` subscribes and lists each wired kind on its own into `useMediaStore` (a kind that fails to load fails only its slot) (events during the load are replayed on top; a second open of the same game shares the load), `closeMedia()` unsubscribes and aborts uploads. `createScene` (refuses at the local limit as `limitReached` without a request; a 400 whose body names a file (`data.<field>.code`) is `fileRefused` with the field and reason, shown under that field, for update too; an empty-`data` 400 first looks for a scene with that id (in the store or by one read: a retry after a lost answer) and returns it, and only without one, under the limit, is `limitMayHaveChanged`), `updateScene` (when it is the live scene and its stored files changed, re-publishes the stage; a failure there is `stagePublishFailed` carrying the saved scene, and `republishScene` retries that alone), `deleteScene` (a live scene is taken off the table first and kept if that fails). Failures the form words are `MediaWriteError` (`MediaWriteError<S>`; `saved` is the entry a `stagePublishFailed` carries, typed as the kind's entry) (`limitReached`, `limitMayHaveChanged`, `fileRefused`, `notMaster` after a 404 re-read of the game, `stagePublishFailed`, `aborted`). Writes check the session and that the store still holds the game, so a late answer never refills a cleared or switched store; closing the session or moving to another game aborts the uploads. The session follows the table: `composables/useMediaSession` (called once in `app.vue`) opens it while the open table is a game I master, otherwise closes it (the connection only gates opening: a blip neither aborts an upload under way nor drops a loaded list, and the return of `ok` re-opens the same game in place); `retryMedia()` is the panel's Try again. A player's client never requests `scenes`, `sounds` or `images`
- `upload.ts` — `sendForm(method, path, form, onProgress?, signal?)`: multipart create or update through `XMLHttpRequest` (fetch reports no upload progress) with the SDK's token; a silence limit of `BOOTSTRAP_TIMEOUT_MS` restarted by every progress event, so a long upload stays alive; an aborted `signal` rejects with `isAbort`
- `pb.ts` (client and row types), `shapes.ts` (shape checks for stored data), `limits.ts` (`HISTORY_LIMIT`)

## Accounts (`app/transport/auth.ts`, `app/features/sign-in/`)

The cabinet and the game tables need a signed-in, verified account; the landing and the offline table never ask for one. Sign-in is a one-time email code only (PocketBase OTP on `users`, 8 digits, 3 minutes). PocketBase sends a code only to an existing user, so `requestCode()` first creates the user with a random throwaway password and ignores "email already exists". A successful code sign-in marks the account verified. Stored per user: `email`, `name`, `language`.

- `authHelpers.ts` — pure helpers with unit tests: email/code sanitising, `defaultDisplayName`, error classifiers, `resolveLanguage`, `authGate(path, signedIn, name)` → `'sign-in' | 'name' | 'none'` (`'none'` for `/` and `/offline…`; the cabinet shell and the table shell both go through it)
- `auth.ts` — `currentUser`, `signedIn`, `requestCode`, `verifyCode`, `restoreSession()` (`'signed-in' | 'signed-out' | 'unreachable'`: 401/403 signs out; a network failure, a 5xx or a 404 — Traefik's answer while the backend redeploys — keeps the token and lets the overlay handle it), `updateProfile`, `deleteOwnAccount`, `clearSession`
- `session.ts` — `watchSession()` (started by the bootstrap plugin) is the one place that reacts to the sign-in state: signed in → `bootstrap()`, signed out → stop the online session and clear the three stores. It also catches sign-in/out in another tab, which the SDK syncs through the `storage` event. `bootstrap()` and every reload check `canLoadOnline(mode, signedIn)`, so a reconnect after sign-out loads nothing
- `app.vue` renders `SignInView` (email → code, or the display-name step when `name` is empty) in place of the cabinet or table layout while `authGate` is not `'none'`; the URL is kept, so a deep link opens after sign-in. Its "Play offline" (and the server-down overlay's) navigates to `/offline`; the email step's "← Home" link goes to the landing `/`
- Language: on sign-in an empty profile language takes the device's; afterwards the profile wins, and the language switches (`LocaleSwitch` on the profile, the sign-in screen and the landing) write to it while signed in (`useAccount().setLanguage`): in online mode, and on the landing in either mode (a cold start at `/` runs offline). The offline table's switch never writes to it, so entering the cabinet from `/offline` resets the language to the profile's (`restoreSession()` → `syncLanguage`)
- **Profile** (`/profile`, `features/profile/`): change name (`RenameSheet`), email, language, install, version, sign out (gold confirm), delete account (danger confirm; games the account runs stay, masterless). Sign out and delete first land on `/` (never gated) and only then clear the session (`watchSession` stops the online session and clears the three stores), so the sign-in screen never shows on `/profile`; `deleteOwnAccount` therefore deletes through `pb.send`, not `collection('users').delete()`, which would end the session itself. Offline data is untouched. The install row reads state that `pwa/useInstall.ts` collects from startup (`listenForInstallPrompt()` in `plugins/04.pwa-register.client.ts`): the browser fires `beforeinstallprompt` once per page load, long before the profile opens
- Stories use the in-memory auth in `.storybook/mocks/pb.ts` (`signInMock()`, `WRONG_CODE`)

**Server unavailable.** In online mode, while `connection === 'down'`, `app.vue` shows `ServerDownOverlay`: a Reka alert dialog over a blurred veil, with the app underneath made `inert`. It shows a reconnect counter, **Retry** and **Play offline** (navigates to `/offline`); it is never shown on the landing or the offline table; with no internet (`navigator.onLine` false) the text says so. It disappears on its own once the server answers and the data is reloaded. The route guards do not redirect away from a deep link while online data has not loaded; the party and level-up pages re-check once it has.

## Stores (`app/stores/`)

The game-data stores (characters, roll history, change log) do not persist themselves; the app mode decides where their data comes from and goes. Only the creation store persists itself, through `pinia-plugin-persistedstate`.

- `useCharactersStore` — State: `list`, `activeId`, `meta` (`Record<id, CharacterMeta>` = `{ owner, game }`, online only). Getters: `active`, `getById(id)`, `metaOf(id)` and `metaView` (both normalise a game unknown to the store to free, `game: ''`; raw `meta` holds the stored value and is for transport bookkeeping), `inScope(id)` (at the open table; offline always true), `canEditCharacter(id)` (offline always true). Actions: `add`, `dispatch(id, cmd)`, `remove`, `setActive`; a scope change clears an `activeId` that is not in the new scope, and the Dice drawer rolls only for an active character in scope. Auto-records change-log entries on `dispatch` for active characters. `dispatch` refuses a character I cannot edit (error toast `errors.readOnly`, no write); a write that fails with 404 on a teammate's character drops it locally with `errors.characterGone` instead of rolling back.
- `useGamesStore` — `games`, `members` (with the user's display name from `expand: 'user'`). Getters `byId`, `membersOf(gameId)`, `active` (the game of the current scope). Filled by `bootstrap()`, realtime (`games`, `game_members`) and `transport/games.ts`
- `useLibraryStore` — one game's library at a time: `gameId`, `monsters`, `items`, per-kind `status.{monsters,items}` (each `idle` / `loading` / `ready` / `failed`); filled by `transport/library.ts`; cleared by `stopOnline()`, and by `useGamesStore` whenever that game's master changes or the game goes (`setAll`, `upsertGame`, `removeGame`), so a former master never keeps the list
- `useEncounterStore` — the master's open encounter, one game at a time: `gameId`, `status`, `refreshFailed`, `state`, `monsters`, `hits`, and per-device UI state that is never stored: `panelOpen`, `selectedMonsterId` (a monster that dies, on any device, stops being selected), `expanded` (the open cards). Filled by `transport/encounter.ts`; cleared with `useLibraryStore` (on a master change, a game leaving the store and `stopOnline()`)
- `useStageStore` — `byGame` (`Record<gameId, Stage>`), `soundArrival` (per game, how the sound slot's current value arrived: `live` or `load`, and when; written before the stage, and moved only when the sound's key changes, so a scene or picture change never makes an old one-shot look fresh; nothing reads the other slots' arrival, so it is not kept), `stageOf(gameId)` (an empty stage for a game with no row), `soundArrivalOf(gameId)`. Every member's; filled by `transport/stage.ts`, cleared by `stopOnline()`, a game leaving the games store drops its stage
- `useMediaStore` — the master's scenes, sounds and images for the open game, one game at a time: `gameId`, `scenes` / `sounds` / `images` each `{status, list}` (images are `TableImage`s; actions `startLoading(gameId, kinds)` (moves only the wired kinds' slots; an unwired one stays `idle`), `setList(kind, …)`, `setFailed(kind, …)`, `put(kind, …)`, `remove(kind, …)`) (`idle` / `loading` / `ready` / `failed`; a reload of the same game keeps the list). Every write takes the game id and is ignored for another game. Filled by `transport/media.ts`; cleared with the library (master change, a game leaving, `stopOnline()`)
- `useToolPanelsStore` — which of the master's own tray cards are open (`open.scenes`, `open.sounds`, `open.images`), per device, never stored; the encounter's flag stays in `useEncounterStore`. Cleared when another game's table opens, on a master change of the open game and by `stopOnline()`
- `useMediaPrefsStore` — this device's choices: `sound` (`'unset'` until asked, `'on'`, `'off'`), `volume` (0..1), `background` (show scene pictures). Persisted under `wod.media.v1` and never cleared: not by sign-out, a mode switch or another account on the same device
- `useCreationStore` — wizard state per mode: `draftId`, `step` (1–3), persisted under `wod.creation.v2`
- `useChangeLogStore` — recent gameplay changes (HP, XP, inventory) for the unified log
- `useRollHistoryStore` — dice roll history (3D dice rolls + manual)

It is bookkeeping and never cuts or swallows a sound a device still plays or is about to start (a slow download, a slow write, an under-reported duration, a skewed clock), so it is late. While this device plays the overlay (`playingHere`: in its playback target, or played to its end), the clear comes `ONE_SHOT_CLEAR_GRACE_SECONDS` (15 s; `graceSeconds` lets stories shorten it) after `onOverlayEnded`, the key re-checked when it fires, with a clock backstop at `startedAt + duration + max(ONE_SHOT_CLEAR_MIN_TAIL_SECONDS (30 s), duration / 2)` when the duration is known and none when it is not; otherwise (sound off, not played because overdue) the clock alone, at that same time with a known duration and after `ONE_SHOT_UNKNOWN_CLEAR_SECONDS` (an hour) with an unknown one (not in the sounds list, or the list failed) (`oneShotClearDelay(sound, duration, now, playingHere)` in `domain/stage.ts`; a unit test keeps the grace above both ready fallbacks of the shell with room to spare). `STALE_ONE_SHOT_SECONDS` only decides whether a device plays a found one-shot. It goes with the scope
- `useStagePlayback()` — called once in `app.vue`: hands the open game's stage, read through this device's choices (`playbackTarget`), to the audio service (the scene sound only when its URL changes, synchronously, so turning sound on inside a click starts the scene before the unlock that follows; the volume when it changes; no stage, offline, signed out or off the game routes means silence) and returns `backdropUrl` for `GameLayout`. The master's sound goes to `audio.setOverlay` (key from `overlayKey`, synchronously like the scene; sound off or no overlay worth playing means `setOverlay(null)` and no URL). One sync watcher updates the memory below and only then hands the overlay to the service (also after `onOverlayEnded`), so a direct switch from one key to another never passes `null` in between. While sound is `on` and a stage is open it calls `audio.arm()` (not for `off` or `unset`: an `unset` device is primed by the prompt's button), so the first tap anywhere primes the pool, the master's first Play included, since the listener runs in the capture phase. Every overlay key seen at an open table gets one record in a per-game memory (`OverlayMemory` in `domain/stage.ts`, `nextOverlayMemory`, held in a ref here) at its first sight: how it arrived (`live`: a realtime change or my own publish; `load`: a snapshot, a reload, `loadGame`), the local time, whether it loops, whether this device plays it (decided once, at the first moment sound is on, from the record's own source and time, never from the store's later values: a loop always plays; a live one-shot plays while it is at most `STALE_ONE_SHOT_SECONDS` since first sight, so sound turned on much later skips it; a found one follows the `startedAt` rule) and whether it ended. The record survives the stage's sound going to null and is forgotten only when the open game changes, so a rollback (a failed write restores the stage as a live value), an echo or a reconnect snapshot never makes a key new or fresh: a skipped or finished one-shot is never played, a loop that should sound does (a rollback to a loop replaced meanwhile hands its key back, so the service restarts it from the start). A one-shot that ended, or stopped being the overlay (replaced, stopped, sound off), is retired. How the value arrived comes from the stage store (`soundArrivalOf(gameId)`: `source`, local time; the sound slot's own, so an unrelated change never refreshes it; written before the stage; read only at a key's first sight); a reconnect's `reloadOnline` leaves `bootstrapStatus` at `ready`, so readiness cannot tell a load from a live change. No overlay plays before its decision. It also calls `useOneShotClear()` (`useStagePlayback({ clearGraceSeconds? })` passes the grace through). Its parts: `useStageTarget(memory?)` (`stage`, `target`, `backdropUrl`, `wantsSound`: the stage carries a sound, whatever this device chose) and `useSoundSwitch()` (`blocked`, `turnSoundOn()` (prefs `on`, then `unlock()`; call it straight from the click), `turnSoundOff()`)

The in-game `StatusHeader` shows HP / XP / armor / equipped weapon damage with `InfoPopover` breakdowns. Armor and damage are read-only in the header — armor type is set by equipping items in the Inventory panel. HP and XP are edited in `HpControlsPanel` (mode on `SegmentedFilter`, a local amount on `Stepper size="lg"`, written once by the submit button) and `XpControlsPanel` (steps on `Button size="sm"`, a typed value on a `lazy` `Stepper` with `hideButtons`); the coin popover's field, the damage and armor effects and the base stat edit in `StatsPanel` are `lazy` too. The stories count `characters.update` calls to prove one write per edit.

In-game tabs (`inGame.tabs.*`): **Main** (stats/skills/abilities) → **Inventory** → optionally **Magic** → **Notes**. There is no Combat tab.

## Games and permissions

Games exist online only; the server is the authority (see the workspace `CLAUDE.md`), the client mirrors its rules. `utils/permissions.ts` `canEdit(meta, me, game, members)`: the owner always edits; a master edits a player's character only while that owner is still a member of the game; everyone else reads. Nothing outside the stores decides this: `dispatch` and `useDiceRoller` (`roll`, `rollBatch`) both check `canEditCharacter` and refuse with `errors.readOnly` (no write, no animation, no history). The UI hides the controls through `useSheetReadonly()`, so the guards are the second line.

**Who may add items** (WODU-57, the owner's decision; it reverses the WODU-9 rule that closed the catalog in a game with a master): the book catalog and "Ask the GM" are open to whoever may edit the character, in the creation wizard, offline, on a free character and in any game. In a game with a master, the master also hands items out from the item library, on any created character there: `canGiveFromLibrary(status, meta, game, me)` in `utils/permissions.ts`. Nobody creates own items. UI-only: the server cannot enforce it (items are inside the opaque `data` blob).

**Purchase feedback** (`CatalogSheet`, shared by the inventory and the creation wizard): the sheet takes the `inventory` and answers to what changed in it and in `coins`, not to the click, so an item that arrives through "Ask the GM" shows too. A row whose count went up flashes, its icon and its "in backpack ×N" `Pill` (`ownedByTemplate` in `domain/inventory.ts`) pop, and a status line announces it; coins going down show the spent amount beside the number. Only the Buy button's check mark follows the click; the label stays under it, so the button keeps its width and its name. Each animation replays through a `:key` that counts arrivals.

- Invite code: 8 chars from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, shown `XXXX-XXXX`, link `<origin>/join/<code>`; input accepts lowercase, spaces and the dash (`utils/inviteCode.ts`).
- Join: `/join/<code>` signed out → `app.vue` looks the code up (`findGameByCode`) and shows the game name as a banner on the sign-in screen; the URL survives sign-in. A reset or wrong code shows "invite not valid" with a way home, never a half-join.
- Game table: players panel lists the game's characters (owner name per row), head with role pill and `GameMenu`: for the master Game settings, Bring one of mine, Home (the Encounter, Monsters, Items, Scenes, Sounds and Images rows are `MasterTools` in the panel, not in the menu); for a player (and everyone in a masterless game) Invite and Members read-only, Bring one of mine, Home, Leave.
- Game settings (`game-settings`, master only): rename (Save disabled while unchanged or invalid; inline "Saved." / failure), invite (`InvitePanel`), members (`MembersList`: Remove and Make master, each behind a danger confirm), delete game (danger confirm, `exitGameQuietly`). **Master transfer**: `transferMaster` sets `games.master` to another member (the server refuses non-members); the former master lands on the game table with `games.members.transferred`, keeps their own characters and from then on reads the others' sheets read-only. A masterless game shows `MasterlessNotice`; "Become master" races are decided by the server, the loser gets `games.claim.taken`.
- **Encounter** (WODU-11, master only): the panel, its three collections and the hits are the master's alone. The server lists them only to `game.master`, so a player never receives a row or an event, and the client of a non-master never requests them; the master is the only one who opens the panel, and a transfer takes it from the former master at once (`useEncounterSession`). What reaches players is the monsters' dice: `roll_events` rows with no character, carrying the instance's numbered name, formula, dice and total, and nothing else (no HP, armor, notes or conditions). Applying damage to a character is an ordinary `APPLY_DAMAGE` through `dispatch`, so it shows as the usual change entry and never as a hit. Offline mode and masterless games have no panel.
- **Scenes, sounds and the stage** (WODU-60): the master keeps a game's scenes (`scenes`, master-only like the encounter: the server lists and sends them to `game.master` alone, and a player's client never requests the collection) and turns one on by publishing the game's stage. Players receive only the stage: the scene's id and its two `FileRef`s, never its name or the rest of the list, and fetch the files by URL. Each device decides for itself what it plays and shows (`useMediaPrefsStore`): sound is asked once while it is `unset`, volume and the background are local, and what a device has off is never downloaded. **Sounds** work the same way: the `sounds` collection is the master's alone, and players receive only the stage's `sound` slot (id, `FileRef`, loop, `startedAt`), never a sound's name or the list. On every member's device that sound plays as an overlay that silences the scene's ambient sound, which comes back from where it paused when the overlay stops or a one-shot ends; a direct switch from one sound to another keeps the ambient silent throughout. Only the master's client writes the stage, including the clearing of a finished one-shot (`useOneShotClear`), so a one-shot whose master is away stays on the stage until the master's table opens again and clears it as overdue; meanwhile a device that loads it more than 5 s after its start does not play it. A transfer takes the scenes and sounds from the former master at once (`useMediaSession`); the stage stays as it was until the new master changes it. Offline mode and the free table have no stage, and masterless games nobody to change it.
- Per sheet (`SheetActions`): "Rename" for whoever may edit the character (`canEditCharacter`; offline everyone), opening `RenameCharacterSheet` (name and true name, each written only when changed); "Take out of the game", and for the master "Give to a player", on my own characters only.
- **True name** (WODU-30): `canSeeTrueName(meta, me, game)` in `utils/permissions.ts`, read through the store's `canSeeTrueName(id)` (offline always true): online only the owner and the master of the character's game see it. UI-only, like `canGiveFromLibrary`: the name stays in the opaque `data` every member reads, and that is accepted. `StatusHeader` shows it through `TrueNameRow`, masked by stars of a fixed length until clicked; the revealed state is never stored.

## Localization (`app/locales/`)

- Trilingual (en/ru/uk), switchable at runtime. `app/locales/en.ts` is the **structural type authority** (`type Messages`); `ru.ts` and `uk.ts` are declared `const messages: Messages`, so `vue-tsc` fails the build on any key missing from (or extra in) any of the three. Add a new key to all three dictionaries together.
- Components use `t('key')` from `@/locales` for UI strings. Game vocabulary (skill/ability/class/stat/gear/cantrip/sphere-preset names) does **not** go through raw `t()` — reach it through the helpers in `app/locales/content.ts` (`skillName`, `abilityName`, `className`, `gearName`, `cantripName`, etc.), which resolve under `content.*` and are guarded at compile time by the `_guards` tuple in that file.
- Allowed inline: `console.*`, developer-only errors, technical strings (CSS classes, localStorage keys, event names).
- Existing hardcoded strings are migrated as files are touched — no mass migration.
- Key style: `section.subsection.name` in camelCase (e.g. `header.hpLabel`, `inventory.emptyState`). Group by screen/feature.

## Colours and tints (`app/assets/main.css`)

Every colour in the UI comes from a token in the `:root` block of `main.css`. **A new tint is a new token, not a literal.** `utils/logger.ts` console colours are not UI and stay as they are; outside `app/`, `nuxt.config.ts` and `public/site.webmanifest` keep their own copy of the page colour for the browser.

- **Naming:** `--vtt-<family>-a<NN>`, where `NN` is the alpha in percent and the value is written `rgba(r, g, b, a)`: `--vtt-gold-a35` is `rgba(140, 106, 58, 0.35)`. `a00` is fully transparent. A family has one RGB; most equal a palette token (`gold` is `--vtt-border-gold`, `sunken` is `--vtt-bg-sunken`).
- **`*-glow` families** (`danger-glow`, `success-glow`, `info-glow`) keep the palette's colours, not the lightened text tokens: WODU-33 lightened text only.
- **Plain tokens** cover what has no family: `--vtt-toast-error-*`, `--vtt-hp-*-end`, `--vtt-sphere-*`. `--shadow-*` and `--glow-*` keep their literals and mirror `palette.html`.
- **Do not reuse a close tint to save a token.** A tint can set the contrast of the text on it, and the worst point of a gradient or a stack of tints sets it, so the number has to be measured on rendered pixels. Two tokens merge only when the lowest-pixel contrast of every text element does not drop. More tokens beats lower contrast.
- **Guards in `app/assets/tokens.test.ts`:** no colour function (`rgba()`, `hsl()`, `oklch()`, …) outside the `:root` of `main.css`; no hex anywhere under `app/` outside it and `logger.ts`; each alpha token matches its family and its name; every `var(--vtt-*)` used under `app/` is defined (a typo silently draws nothing, and the browser reports no error); text on a tint meets AA, by a table of text token, fill stack and backdrop, whose top fill must be in the `background` of the rule it names. A row under AA holds a floor in `KNOWN_LOW` at its computed value, so any change shows in the diff; lowering one is a decision, not a fix. Named colours (`red`, `white` in a `color-mix`) are not guarded.
- **What that table does not see:** it is computed from tokens, not pixels. It does not model `opacity` or `backdrop-filter`, a row marked `artwork` computes over the flat page instead of the image behind it, and a row `over: 'artwork'` has no number at all; a row `over: 'any'` computes over a white pixel, which an opaque fill holds whatever the image shows, but a patch that fades (`.as-brand::before`) holds only at its solid centre. Most of the app sits on the artwork, so a real contrast question needs a rendered measurement.
- **`test-visual` will not catch a small tint change:** its comparison uses pixelmatch's default threshold (0.1), and a shift of several levels passes. Compare exact pixels to prove a tint did or did not move.

## Key Rules

- Creation-only fields are hidden once `status === 'active'`
- No decorative chrome — every UI element must serve a functional purpose
- Offline data survives page refresh and browser restarts (localStorage); online data lives on the server and is reloaded on start
- Domain command dispatch is the only path for gameplay mutations
- Text a person typed is cut with `cutText` (`utils/text.ts`), not `slice`: half an emoji makes PocketBase refuse the whole write
- Bump `version` in `package.json` (patch by default) whenever you change code — the in-app footer surfaces it via `__APP_VERSION__`, so a stale version means stale UI for users
